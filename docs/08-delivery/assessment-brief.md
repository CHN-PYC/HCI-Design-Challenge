> 本文是**要求摘要**；带「建议」的条目是我们的行动提醒，不是原文规定。

## 1. 一句话总览

小组项目，用**以用户为中心的设计（UCD）流程**做出一个**高保真（hi-fi）原型**，并用一套 50–120 页的幻灯片讲清「设计如何一步步演化」。最终交付三样东西：主幻灯片、viva 用短幻灯片、A1 海报；第 11 周参加 poster session 和 viva。

| 交付物 | 要求 | 截止 |
| --- | --- | --- |
| A1 Poster | 概括问题、设计演化与最终设计，供其他组点评 | **12 月 2 日（周三）12:00**，Week 10 |
| 主 Slide deck | 50–120 页；建议每周累积 10–15 页，最终约 90–120 页 | **12 月 4 日（周五）17:00**，Week 10 |
| Viva deck | 最多 12 页，覆盖指定 8 个主题 | 同上，12 月 4 日 17:00 |
| Poster session | 展示海报，互评 | Week 11 |
| Viva | 与评估人面对面，围绕设计、过程与理解提问 | Week 11 |

## 2. 题目要求：Sensing for Benefit

**核心命题：设计一个主动式（proactive）系统，在合适时机介入，为用户或社会创造实际收益。**

必须满足：

- **主动 + 交互**：既能响应输入，也能主动发起建议、提醒、打断或行动；不能只是被动展示信息。
- **接入外部数据**：至少整合一个外部来源——手机/手表传感器（GPS、活动等）、IoT 传感器、API、数据库、扫码后的信息查询等；不能是孤立 App。
- **有实际干预**：在关键时刻提示、建议或改变流程，而不是只给信息。
- **重视用户体验**：考虑既有经验、同伴压力、社会期待、游戏化、愉悦感、幽默、个人目标与进度等。
- **有影响力**：可选宽泛人群或特定子群；可家用、便携或两者结合；要追求 significant impact。

可选方向（仅为示例）：健康饮食、减少社交媒体、环保行为、独立生活、神经多样性支持、信息茧房识别、减少屏幕时间、绿色通勤、节能、减少拖延、学习投入等。

技术上可自由选择：视频、声音/语音、动作识别、手机/手表传感、IoT、外部 API 均可。也允许用 GenAI 辅助做交互原型或可运行系统，但**必须讲清做了什么、为什么、如何迭代与修正，并且自己能解释生成结果**。

最终必须落到 UCD 流程：**Empathise → Define → Ideate → Prototype → Test**。

## 3. 主 Slide deck：评什么、怎么写

### 3.1 核心叙事

不是「先有想法 → 展示设计 → 再补几个方法截图」，而是要让每个方法**与设计演化强绑定**：

- 用了哪些 UCD 技术；
- 每种技术贡献了什么、排除了哪些选项、学到了什么；
- 设计取向如何影响工作；
- 每个设计决策是如何得出的。

每个阶段都回答四个问题（viva deck 也明确要求）：

1. 这一阶段想弄清什么？
2. 打算怎么做（用什么技术）？
3. 学到了什么？
4. 如何影响下一阶段？

呈现设计选择时，务必写：**考虑过哪些方案 → 为什么否决 → 为什么选这个**。允许用标注（annotated notes）和作品集式摘要，不必重写成完整报告，但要有连贯叙事。

### 3.2 典型内容结构

| 阶段 | 应展示的证据 |
| --- | --- |
| Empathise | 可能问题领域的讨论；现有证据综述（网络检索、竞品 App 评测等）；用户研究（问卷、焦点小组、民族志等） |
| Define | 问题定义；必要的补充用户研究；personas 与 scenarios |
| Ideate | 多种可能方案；创意技术；草图；可让用户参与 |
| Prototype | 方案细化草图；用于回答具体问题的 lo-fi 原型；wireframes；Arduino/概念验证等 |
| Test | 用用户/persona/scenario 评估；实验性验证 |
| Review | 回看早期阶段：哪些想法被证明好、哪些被丢弃、为什么；说明各阶段如何衔接 |

## 4. Viva deck（≤12 页）必须覆盖

1. 问题空间的发散：可能解决哪些问题、选了哪个、为什么；
2. 对所选问题的有目的调查：多种共情方式；
3. 聚焦方案：personas、scenarios、具体问题；
4. 原型方案的发散：大量例子；
5. 选择理由；
6. 原型及学到的东西；
7. 迭代到 hi-fi 原型；
8. 对最终产品的评论。

对以上每一项，都要回答：想弄清什么 / 怎么做 / 学到什么 / 如何影响下一阶段。

## 5. 评分维度

| 维度 | 看什么 |
| --- | --- |
| **Deck** | 文档本身：连贯性、呈现、清晰度 |
| **Process** | 最终设计产生的过程 |
| **Substantialness of Achievement** | 方案的复杂度与适配度；理解、反思、分析的深度 |
| **Management** | 项目规划方法与团队管理 |
| **Poster** | 问题、设计演化、最终设计的总结 |

评分档要点：

- **80–100 Outstanding**：方法严谨且合适，论证有充分证据，可用于奖项提名或后续研究。
- **70–79 Excellent**：对重要概念与设计方法理解深入；问题定义与背景综述超出课程常规；能明确区分**证据与观点**；评估有证据支撑且具批判性；全过程严谨、无重大错误。
- **60–69 Very Good**：批判性思维与设计/科学/工程方法扎实，评估方法可靠、无重大遗漏——这是**通常期望达到**的水平。
- **50–59 Good**：基本达标但有一两处重大概念错误或缺失，例如评估靠观点、问题较表面。
- **40–49**：问题定义纯轶事、方案只需很基础技能、评估只是朋友随手试用等。
- **30–39 Fail / 0–39 Incomplete**：问题不够实质，或方案/评估不严谨，或大量关键部分缺失。

## 6. 团队规则

- 小组评分，**所有成员同分**。
- 大部分时间应协作：会议、讨论、白板、纸原型；可偶尔 2–3 人并行分工，但最佳结果来自整合讨论。
- **每个人都要参与每个阶段**。
- 若对均分有异议，全组需签署一份写明分数分配的文件；评估人会参考但不一定完全照办。无法达成一致时评估人将组织会议。

## 8. 自查清单（建议）

- [ ] 方案确实「主动」：定义清楚的触发条件、干预动作与用户可控性。
- [ ] 至少一个真实外部数据源（传感器/API/IoT），并在原型中可见。
- [ ] 每个设计决策都有「备选 → 否决理由 → 选择理由」记录。
- [ ] 每个阶段都有原始证据（问卷、访谈摘录、草图、测试记录），并回答四问。
- [ ] 评估不是「朋友试了一下」，而是有任务、指标、参与者与结论。
- [ ] 主 deck 页数在 50–120；viva deck ≤12 且覆盖 8 个主题。
- [ ] 海报在 12 月 2 日 12:00 前完成并打印为 A1。
- [ ] 12 月 4 日 17:00 前提交两套 deck。
- [ ] 每位成员都能独立讲清全过程与自己的贡献（viva 防「只用 LLM 不懂细节」）。
- [ ] 若使用 GenAI 生成原型/代码，deck 中说明用途、迭代与人工修正过程。
